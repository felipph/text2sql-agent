1. Resumo executivo

txt2sql não é um serviço HTTP: é uma biblioteca Python que, a partir de um YAML de bancos/tabelas e de um LLM Azure OpenAI, devolve um CompiledStateGraph LangGraph pronto para invoke/stream.

Tese central

O diferencial não é “gerar SQL com LLM”, e sim separar intenção semântica de execução: IntentPlan grounded → roteamento determinístico de shard/path → Policy Gate fail-closed → execução na origem (simple) ou via materialização DuckDB (analytical).

Fan-out entre shards é proibido — o discriminator resolve um destino físico, não uma varredura. ADR-0002 · docs/arquitetura.md

2. Propósito e domínio de negócio

O domínio ilustrado nos exemplos (examples/recebiveis.yaml, playground) é consulta analítica sobre títulos de crédito (recebíveis) particionados por CNPJ em múltiplos bancos físicos, com cadastro de clientes no banco principal. A biblioteca, porém, é genérica: qualquer schema descrito no YAML.

Problema que a lib resolve

Consultar vários bancos físicos e tabelas particionadas com cargas analíticas sem sobrecarregar o OLTP — materializando extratos em DuckDB quando necessário (README, ADR-0003, ADR-0006).

Três diferenciais (README)

  1. Multi-banco + sharding determinístico — (discriminador) → (banco, tabela_física).
  2. Schema declarativo ou discovery — YAML com colunas/descrições, ou reflection SQLAlchemy.
  3. DuckDB intermediário — por thread_id no dual-path; efêmero por turno no ReAct.

4. Arquitetura geral

Padrão predominante: grafo de estado tipado (LangGraph) com middleware de política e camadas de dados plugáveis. A app hospedeira é o boundary de I/O; a lib é o núcleo de decisão + execução SQL.

API pública estável

Exportada em txt2sql/__init__.py: build_agent, load_config, AgentConfig, ShardResult, QueryTimeoutError (+ __version__). Módulos internos (guardrail, policy, intent, db.*) são úteis mas sem garantia de estabilidade (api.md).

5. Fluxo de execução dual-path

Após build_agent(config, checkpointer=..., dual_path=True), o caller invoca o grafo com HumanMessage e, tipicamente, configurable.thread_id.

  1. init_state — prepara Budget e reusa sessão DuckDB do thread_id se existir.
  2. interpret_intent — LLM → IntentPlan; validate_intent contra índice de colunas.
  3. ask_clarification (condicional) — HITL via interrupt se houver checkpointer; senão pergunta e encerra.
  4. resolve_and_route — resolve_routing + route_execution → simple ou analytical.
  5. Simple: generate_sql → Policy Gate → exec_source → verify → answer.
  6. Analytical: sufficiency_gate → plano/materialize → SQL DuckDB → verify → answer.
  7. verify pode refinar (volta a generate_*) ou materializar de novo, sujeitos a budgets.

Critérios simple vs analytical

Evidência em path_routing.route_execution:

  • shard_routing.mode == "multi" → analytical
  • Tabela com force_analytical / requires_analytical → analytical
  • Tabela DuckDB + métrica agregada ≠ none ou group_by → analytical
  • Caso contrário → simple
Incerteza / possível divergência: triggers DuckDB order e join são honrados por needs_duckdb no caminho ReAct; route_execution (dual-path) não os lista explicitamente — comportamento pode diferir entre os dois grafos.

ReAct legado (dual_path=False)

Loop em agent.py: após intent, o LLM chama tools (sql_db_schema, sql_db_query, opcionalmente resolve_shard, materialize_sharded_table). DuckDB é sessão in-memory por turno, não DuckDBSessionStore.

7. Intent, Policy Gate e Guardrail

IntentPlan

Structured output com status (ready | needs_clarification), rewrite da pergunta, entities, filters, metrics, group_by, joins, order_by, limit, clarification e assumptions. Validação fail-closed de IDs de tabela/coluna contra SchemaLoader.get_column_index.

Policy Gate (check_sql_plan)

  1. Chama validate_sql + allowlist de tabelas
  2. Rejeita nomes físicos já materializados (usar nome lógico no DuckDB)
  3. routing_rejection_reason (shard não resolvido / cross-DB)
  4. Em source_extract: bloqueia agregação na origem se force_analytical
  5. Injeta LIMIT se ausente (default 500 000)

Guardrail (validate_sql)

Fail-closed: query vazia, denylist textual (fora de literais/comentários), exatamente 1 statement, raiz Select/With/Union, proíbe DML/DDL/controle em qualquer profundidade da AST, funções com side-effect, allowlist opcional pós-qualify. Complementado por listener no DatabaseRegistry quando read_only.

Princípio de segurança

Qualquer dúvida → rejeitar (AGENTS.md, ADR-0004). Não há modo “best effort” no gate.

IDs de tabela no YAML são lógicos; nomes físicos podem diferir após shard. Dialetos evidenciados nos exemplos: postgres, tsql (YAML dialect).

9. Configuração YAML

load_config(path, override_connections=None) produz AgentConfig. Connection strings vêm de connection_env (ex.: MAIN_DB_URL), não de nomes fixos — ou de override_connections em runtime. 

dialect: postgres|tsql
databases: [{id, connection_env|connection_string, read_only, query_timeout?}]
tables: [{id, database, name, columns?, sharding?, duckdb?, description?}]
relationships: [{from: {table, column}, to: {...}}]
glossary: [{term, definition}]
agent: {top_k, max_pages, max_shard_discriminators, query_timeout, ...}
llm: {deployment, model, api_version, azure_endpoint, api_key, temperature}
# DuckDBConfig: enabled, trigger∈{always,aggregation,order,join}, fetch_limit, force_analytical
# sharding.resolver: "modulo.sub:funcao" → (str) -> ShardResult

Se o bloco llm estiver incompleto, AZURE_OPENAI_* são obrigatórias (AGENTS.md). trigger: always implica force_analytical=True.

11. Glossário

Shard / discriminator
Partição física determinada por um valor (ex. CNPJ) via resolver → ShardResult(database_id, table_name).
Fan-out / Fan-in
Fan-out = varrer todos os shards (proibido). Fan-in = materializar ≥2 discriminadores no DuckDB sob nome lógico.
IntentPlan
Plano semântico pré-SQL (structured output), validado antes do roteamento.
HITL
Human-in-the-loop: clarificação via interrupt + Command(resume=...) com checkpointer.
thread_id
Chave LangGraph de sessão e chave do DuckDBSessionStore.
dual_path / simple / analytical
Dois caminhos de execução no grafo padrão; ReAct é o modo legado.
force_analytical
Obriga path analítico; Policy Gate bloqueia agregação na origem.
Budget
Orçamentos de clarificações, refines, loops de materialização e visitas ao gate.
sufficiency_gate
Decide reuse vs refresh do catálogo DuckDB da sessão.
Tabela lógica vs física
ID/nome no YAML vs nome real no shard após resolução.
fail-closed
Em dúvida (parse, política, intent), rejeitar em vez de executar.

12. Premissas, restrições e requisitos

  • Checkpointer não é criado pela lib — HITL/resume exige injeção pelo caller.
  • Clarificações limitadas por Budget.max_clarifications (default 2); esgotado → finish sem SQL.
  • Queries de escrita rejeitadas; default read_only=True.
  • Sem fan-out; multi-discriminador só via materialização DuckDB.
  • Python ≥ 3.12; Azure OpenAI para uso real (smokes usam LLM falso / SQLite).
  • Materialize em lotes — não usar fetchall na origem (AGENTS.md).
  • API pública só muda com atualização de docs/referencia/api.md (CONTRIBUTING).

Requisitos importantes (produto)

  • Grounding de intent antes de SQL
  • Proteção de OLTP-hot (force_analytical, Policy Gate)
  • Observabilidade opcional (Langfuse)
  • Config declarativa multi-tenant-friendly via YAML + overrides

13. Divergências e lacunas docs ↔ código

gap smoke_test_graph vs ADR-0006

ADR-0006 afirma que smoke_test_graph.py “cobre o caminho compilado” dual-path; o smoke usa dual_path=False (ReAct). Evidência cruzada: relatório de exploração do código.

gap custom_section de recebiveis.yaml

Instrui o LLM a usar tools resolve_shard / materialize_sharded_table, inexistentes no dual-path padrão — texto alinhado ao ReAct legado.

doc duckdb_layer docstring

Ainda descreve sessão “efêmera por turno”; dual-path usa store persistente por thread_id (ADR-0003 / api.md).

doc AGENTS.md Structure

Omite vários módulos (artifacts, routings, middleware, llm, …) e a API listada omitia QueryTimeoutError (presente no código e em api.md).

comportamento triggers order/join

Possível divergência entre needs_duckdb (ReAct) e route_execution (dual-path) quanto a triggers order/join — não determinado com certeza de equivalência.

Não determinado com confiança: métricas de uso em produção, SLAs, topologia real de shards fora dos exemplos, e o papel runtime concreto de grandalf (declarado em pyproject; não documentado na doc de produto lida).
